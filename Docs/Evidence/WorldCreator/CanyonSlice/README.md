## Implemented path

`WorldCliffFacePlanner` links reciprocal absolute-grid candidates only when canyon parent, strata, direction, facing, and rim/toe elevations agree. The existing chunk decorator owns only spans whose first section lies in that chunk. A closed 12-point ring mesh gives the face two stepped strata ledges and a cap; a lower-detail closed mesh supplies collision. The parent and strata key set a stable layer phase. Sparse buttresses and toe fragments load the existing baked `CliffStone_A-E_LOD0-2` Workbench meshes, use LOD groups and simplified box collision, and remain children of the streamed chunk. Spawn, formation, site, approach, route, slope, and chunk-footprint screens limit placement. Static geology writes no save delta.

## Canyon morphology investigation, 2026-09-28

The canonical segment above is only 55.1–56.6 m wide while its endpoint depths are 76.3–86.2 m. A query trace from a generated cliff section at `(415.5, 319.5)` showed 60–77° slopes for the first 40 m beyond its sampled toe. The apparent floor at 16–20 m remained about 58–62° and was route-reserved. A source-linked talus planner therefore produced candidates but its terrain-footprint screen correctly admitted **zero** rocks in the narrow fixture. Placing physical debris there by relaxing clearance would put it on a steep wall or protected route.

`CanyonCrossSection.Shelves` is generated and hashed by `CanyonSystemPlanner`, but the active excavation query currently uses only width and depth in one smoothstep cut. The stored lower/middle/upper shelf values do not yet shape the terrain. A color-only strata treatment also left the monolithic silhouette unchanged; it was discarded in the mirror.

Two **mirror-only topology experiments** used the same seed and canyon segment. [WidenedCanyonExperiment.png](WidenedCanyonExperiment.png) changes the major cross-section width range from 18–112 m to 110–330 m, making this segment 194.5–197.1 m wide while retaining its depth. The latest mirror candidate preserves the original narrower range for local branches. [TerracedCanyonExperiment.png](TerracedCanyonExperiment.png) also uses the segment's existing shelf values as four continuous cut bands. Both images use 6-quad coarse terrain outside 20 detailed chunks, a plain temporary terrain material, temporary lighting, and experimental larger Workbench rocks. The terraced candidate establishes a clearer floor, shoulders and stratified walls, but its blocky repetition and material/contact quality remain unaccepted. It is an experiment, not a production asset or a gameplay view.

The mirror's reported source fingerprint stayed `96ef0728256ce0e5c5524173e588aa7f` even when the code-defined cross-section changed. That fingerprint alone is insufficient provenance for a topology comparison; the code revision and a new topology/version decision are required. The live query/profile/scene remain dirty user-owned work and were not changed for this experiment.

The mirror-only widened/terraced query compiled in Unity `6000.4.0f1`; the focused `UnboundedHybridWorldQueryTests`, `WorldRepresentationCompilerTests`, and `WorldCliffSectionStudyTests` run passed 17 of 17 (`/tmp/booter-canyon-topology-experiment-tests.xml`). Those tests do not prove visual quality, near/middle/far seam agreement, route width, collider contact, save compatibility, or Player performance for the new shape.

A second mirror-only fixture covered 20 detailed 18 m chunks around the same segment. It produced 178 physical cliff spans, 49 enlarged Workbench buttresses, and 97 source-linked talus rocks, with identical object IDs/counts after reverse build order and origin rebase (`/tmp/booter-canyon-terrace-face-20chunks.xml`). Three sequential editor decoration passes took 2609, 2531, and 2537 ms for the 20 chunks. This density is visibly repetitive and has no full-content Player budget proof, so it is not ready for production. The source-linked talus implementation remains mirror-only; the live repository retains the earlier sparse rock pass.

## Limits and next gates

The current pass does not show the canyon through fixed production-camera views, prove rendered terrain-triangle contact, profile a full-content Development Player, or prove two streaming-ring transitions. Middle/far terrain comes from the canonical query, but the new ledge and Workbench detail exists only in near decoration; distance continuity and arrival pop remain unverified. No gameplay smoke test or hands-on traversal was run. The user must review the visual result and traverse it before this becomes an accepted canyon treatment. Do not enable the canyon in the production first area or change topology/save versions on the strength of this receipt.
