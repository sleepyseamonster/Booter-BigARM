## Implemented path

`WorldCliffFacePlanner` links reciprocal absolute-grid candidates only when canyon parent, strata, direction, facing, and rim/toe elevations agree. The existing chunk decorator owns only spans whose first section lies in that chunk. A closed 12-point ring mesh gives the face two stepped strata ledges and a cap; a lower-detail closed mesh supplies collision. The parent and strata key set a stable layer phase. Sparse buttresses and toe fragments load the existing baked `CliffStone_A-E_LOD0-2` Workbench meshes, use LOD groups and simplified box collision, and remain children of the streamed chunk. Spawn, formation, site, approach, route, slope, and chunk-footprint screens limit placement. Static geology writes no save delta.

## Adaptive far streaming candidate, 2026-09-29

The isolated mirror now has a [worker-side adaptive planner](AdaptiveFarStreamingPlanner.cs.txt), [far-landscape integration patch](AdaptiveFarLandscapeIntegration.patch), and [world scheduler patch](AdaptiveFarWorldSchedulerIntegration.patch). Each far tile first presents its original 17×17 mesh. A canyon-containing tile retains an immutable snapshot of canonical vertex positions, normals, and material colors; after near terrain and decoration queues drain, one background task at a time samples and triangulates its high-error cells. The main thread uploads the returned arrays and swaps the visible mesh. Per-cell triangle ranges preserve adaptive detail when near/middle coverage hides or restores parts of a tile. Pending work is cancelled on unload or a busy near window. Static far geometry has no collider or saved runtime delta. The tile key and canonical query/material samples determine the mesh; the selected cells use a stable error and cell-index tie break.

The [focused lifecycle test](AdaptiveFarStreamingTest.cs.txt) and [NUnit result](AdaptiveFarLifecycleResults.xml) passed 1 of 1: the tile began at 289 vertices, upgraded, hid and restored a covered cell, unloaded outside the far ring, and rebuilt with identical vertices, colors, and indices. This exercises the landscape object lifecycle directly in EditMode; it is not a Player camera or visible pop check. The final [focused performance test suite](AdaptiveFarPerformanceTestsResults.xml) passed 10 of 10 after the EditMode mesh-destruction fix.

The [temporary Player route driver](AdaptiveFarPlayerBenchmarkDriver.cs.txt) and three filtered full-content rendered Development Player logs preserve the integration experiment: [immediate upgrade](AdaptiveImmediatePlayerTelemetry.log), [deferred run one](AdaptiveDeferredPlayerTelemetry.log), and [deferred run two](AdaptiveDeferredPlayerTelemetryRepeat.log). All three ran at 1034×546, reached five settled waypoints, logged 49 successful far-tile upgrades, and exited normally. Immediate upgrade had 49/49 adaptive tiles by the first settled stop but showed a 1507 ms first-arrival p99 window. The deferred runs had 0/49 at the first stop, then 34/49 and 26/49 at stop one, and 49/49 by stop two; near terrain and decoration queues were zero at later stops. Their first-arrival p99 windows were 491 ms and 92 ms respectively. The dispersion, differing center chunks from the earlier 17×17 route, and pending work at stop zero prevent a causal performance claim. The temporary driver teleports; it does not prove continuous traversal or absence of visible mesh swap.

This code remains a **mirror candidate**. None of the runtime integration, temporary test/driver, topology, material, scene, or profile changes were copied into live Unity assets. The next gate is a same-center rendered comparison with frame attribution and captured production-camera views at far loading and swap, followed by the user's visual/traversal acceptance and a topology/save-version decision before production cutover.
