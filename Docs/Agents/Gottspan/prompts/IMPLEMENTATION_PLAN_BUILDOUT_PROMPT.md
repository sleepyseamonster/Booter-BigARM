# Booter & BigARM Approved Plan Buildout Prompt

Use this prompt only after an implementation-ready plan has been approved for execution. It is the companion to [`IMPLEMENTATION_READY_PLAN_PROMPT.md`](./IMPLEMENTATION_READY_PLAN_PROMPT.md): the first prompt produces the plan; this prompt builds the approved plan without silently redesigning it.

Replace the bracketed fields. `IMPLEMENTATION PLAN SOURCE` is required and must identify one readable repo path, attached plan, or named source that every checkpoint can reopen. Do not use chat recollection or a loose summary as the plan source.

```text
IMPLEMENTATION PLAN SOURCE (REQUIRED)
[Repository path, attached artifact, or uniquely named approved plan. State the plan revision, commit, or dated section if the source can change.]

EXECUTION AUTHORITY AND CONSTRAINTS
[State the user's current implementation authorization and any approved decisions, protected paths, active owners, prohibitions, deadlines, required proof, or explicitly authorized interactive Unity work.]

Pursue the goal of completing the approved implementation plan named above in the Booter & BigARM Unity repository. Treat that plan as the primary execution contract, refreshed against live repository truth. Before any implementation, open the plan source and restate in your own words: the objective and observable success state; source-of-truth order; owner and active lane; approved scope; preserved behavior and non-goals; required proof; decisions still requiring approval; and the exact implementation completion and stop conditions. Include the plan source path or identifier in every progress checkpoint and closeout so the work remains anchored to the same artifact.

If the plan source is missing, unreadable, ambiguous, materially stale, contradictory with current instructions or live code, missing a required objective/scope/proof/stop boundary, or too vague to implement autonomously, stop before editing. Audit the applicable repository instructions and the plan's cited live surfaces. Resolve only factual drift that does not change the plan's outcome; then report the exact conflict, missing decision, or plan correction required. Do not silently rewrite an approved plan, infer product approval, or use a new task prompt as a substitute for the named plan.

Begin with Batch 0: revalidate the plan and ownership boundary against the current checkout. Read the applicable `AGENTS.md`, Gottspan contract and runtime-load policy, plan-cited standards, current Git status and relevant diffs, affected assemblies and callers, serialized consumers, existing tests and validators, Unity version/packages when material, and `Temp/UnityLockfile` before proposing Unity automation. Classify every existing dirty or untracked file as user-owned unless the current plan and authority explicitly place it in scope. Reopen the actual plan source before each batch; do not rely on memory. If Git state, Unity lock state, assets, schemas, or upstream plan assumptions changed since the plan, decide whether the change is an in-scope factual refresh or a stop for the plan owner/user.

Work only inside the plan's approved execution lane. Gottspan coordinates integration and final evidence; Babineaux owns Unity/editor/automation bridge work; Lorekeeper owns narrative retrieval and synthesis; Gear Ball owns staging, commits, pushes, pull requests, and other GitHub publication. Do not create competing authorities or let one lane absorb another. A request to implement does not authorize a commit, push, release, package change, broad project-setting change, asset purchase, destructive operation, or external action unless the current authority names it.

Preserve the project's actual Unity boundary. Production gameplay belongs in the live TopDown3D C# runtime assembly and namespace declared by its `.asmdef`; Editor automation and validation remain in Editor-only C# assemblies; focused tests remain in the project test assembly; rendering changes may require HLSL/ShaderLab and URP assets; input changes must retain Unity Input System action-map authority. Verify current paths before changing them. `Assets/_Project/Legacy2D/` is reference-only and never a dependency or destination for new production work. Treat each Unity asset and its `.meta` file as a single reference unit: preserve GUIDs, inspect scene/prefab/ScriptableObject/builder/validator coupling, and never regenerate metadata casually.

For any planned gameplay or world-system batch, uphold the plan's procedural-world contract: deterministic world identity and generation version, chunk/region ownership, stable generated-object identity, load/unload/reload behavior, regenerated state versus persisted runtime deltas, save/snapshot versioning and migration, authored constraints/landmarks/narrative anchors, repeated-seed and boundary proof, and relevant performance budgets. Do not introduce an always-loaded scene authority, duplicate generator, duplicate state owner, scene scan, magic identifier, fallback controller, temporary bridge, or backup implementation unless the approved plan explicitly requires, bounds, owns, and tests it.

Execute autonomously in small, dependency-ordered validated batches. At the start of every batch, state the plan source, batch name, objective, exact allowed files/assets, canonical owner, preserved behavior, expected proof, and stop gate. Choose the highest-ROI uncompleted batch only when every prerequisite passed and it directly improves plan completion. Implement the smallest coherent canonical change; update all required callers/serialized consumers/tests in the same batch; then inspect the exact diff, run the plan's narrowest applicable non-mutating validation, record what it proves and does not prove, and self-audit for missed references, serialization/GUID drift, procedural-contract drift, documentation drift, and scope creep. Never advance merely because another nearby improvement is tempting.

Maintain strict player-facing and operating boundaries. Do not change UI/UX, controls, camera behavior, movement feel, animation feel, world rules, save compatibility, economy, security posture, launch posture, performance targets, branch policy, commit/push/deploy state, or another owner's workspace unless the approved plan and current authority explicitly include that change. Preserve the user's foreground application: do not activate, raise, focus, or send keystrokes to Unity during normal work. Do not ask the user to focus Unity for ordinary repository work. Never run batchmode against a Unity project owned by the GUI; do not create or run gameplay smoke tests unless expressly authorized. Interactive scene, visual, physics, input, animation, and feel acceptance remain user-owned unless explicitly delegated.

Use the plan's proof matrix as a contract, not a suggestion. For each completed batch, select the narrowest relevant checks and distinguish: structural/diff/reference proof; Unity compilation/import; focused EditMode or deterministic PlayMode execution; validator results; save/load/unload/reload or determinism evidence; performance evidence under the named scenario; interactive Unity evidence; player-build proof; and Git/publication proof. Verify that a proposed validator is non-mutating before treating it as validation. State the exact command or named gate, result, candidate scope, and limitation. Never claim a higher proof level than was actually achieved; compilation is not gameplay proof, tests are not visual acceptance, a build is not player acceptance, and a commit is not publication or release proof.

Stop immediately and hand off or request direction when: the plan is complete; the next step lies outside approved scope or another owner's lane; a required source is missing or contradictory; a user/creative/canon decision is needed; a package/project-setting/asset-purchase/destructive or release decision is required; a required validator fails and the fix may alter behavior beyond the plan; Unity state prevents safe validation; required proof is unavailable; an existing dirty change overlaps the batch; or remaining work would mostly be churn. Do not patch around a failed gate, weaken a test, skip the required proof, add speculative infrastructure, or continue after the plan's stop condition.

At each checkpoint report:

1. **Plan Source And Current Batch** — exact path/identifier, plan revision if known, and batch/gate.
2. **Restated Contract** — objective, scope, owner/lane, preserved behavior, proof, and stop condition.
3. **Live Revalidation** — relevant repo/Unity/dirty-worktree facts and any plan drift.
4. **Implemented Canonical Change** — exact code, asset, scene, setting, test, or documentation boundary changed.
5. **Validation And Proof Boundary** — checks run, results, and what remains unproven.
6. **Self-Audit And Next Decision** — regressions/scope review and either the next named plan batch or an exact stop/handoff.

At final closeout report: every completed plan batch; exact task-owned files changed; all validation evidence and its limits; unexecuted interactive/build/performance/save/publication proof; preserved unrelated worktree state; documentation or handoffs updated; any explicitly deferred plan item and why; the exact implementation completion state; and the next authorized move. Do not claim completion until the named plan's completion condition and required proof boundary are actually satisfied.
```

## Prompt Stop Condition

This prompt has done its job when the named approved plan is either completed with its specified proof or safely stopped at a specific unresolved boundary. It never grants authority to redesign the plan, expand the product scope, or publish work.
