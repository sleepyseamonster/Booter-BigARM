# Booter & BigARM Implementation-Ready Planning Prompt

Use this prompt when a requested feature, repair, migration, system, tool, or content slice needs a repository-grounded implementation plan before anyone changes production code or Unity content.

Replace the bracketed request and add any current authority or constraints the planner must honor. If no additional constraints apply, omit that section.

```text
REQUESTED WORK
[Describe the requested feature, repair, migration, system, tool, or content outcome here.]

CURRENT AUTHORITY OR CONSTRAINTS
[Optional: name approved decisions, protected files, active owner lanes, product defaults, deadlines, prohibited changes, or required evidence.]

Pursue the goal of creating an implementation-ready plan for the requested work in the Booter & BigARM Unity repository. This is a planning-only task. Do not begin feature implementation, edit product code or Unity assets, run mutating builders or repair tools, change packages or project settings, create gameplay smoke tests, stage or commit feature work, push, publish, or perform release operations. If the user explicitly requests a plan document in the repository, create or update only that plan artifact and any strictly necessary clean routing reference; otherwise return the plan in conversation. Preserve all unrelated and pre-existing workspace changes.

First establish the planning contract. Identify the objective and observable success state; product, creative, repository, Unity bridge, narrative, content, validation, and Git/GitHub owners that actually apply; the active implementation lane and assembly; source-of-truth documents and code or asset paths in precedence order; approved scope; non-goals; behavior and data that must remain unchanged; required proof; decisions already approved; decisions still requiring approval; and the exact planning and later implementation stop conditions. Distinguish user authority from agent responsibility. Use Gottspan for repo-wide coordination and final integration, Babineaux for Unity/editor and automation handoffs, Lorekeeper for narrative retrieval and synthesis, and Gear Ball for commits or GitHub publication. Do not create a competing owner or silently broaden one lane into another.

Research the live repository before deciding. Read the applicable `AGENTS.md`, Gottspan's contract and runtime-load policy, `Docs/DOCS_INDEX.md`, the task-specific canonical standards or program plans, current Git status and relevant diffs, the current Unity version and packages when material, assembly definitions, the production scene and serialized consumers, relevant ScriptableObjects/prefabs/materials/shaders/input assets, existing tests, validators, builders, and documented automation. Inspect callers and downstream consumers, not only the file named in the request. Check whether `Temp/UnityLockfile` exists before proposing any Unity command. Treat memory, old plans, snapshots, and reports as leads that must be refreshed against live files. When sources conflict, follow the repo's source-of-truth order and name the conflict rather than averaging it away.

Plan for the project's actual technical boundary. Production gameplay is C# in the live TopDown3D runtime assembly and namespace declared by its `.asmdef`; editor tooling and validation are C# in an Editor-only assembly; focused automated tests belong in the project test assembly; rendering work may require HLSL/ShaderLab plus URP assets; input work must preserve the Unity Input System action-map authority; data work may involve ScriptableObjects, versioned serializable C# DTOs, JSON saves, scenes, prefabs, materials, or other Unity-serialized assets. Verify those current paths and names before citing them. The preserved `Assets/_Project/Legacy2D/` tree is reference-only and never the destination or dependency for new production systems. Treat every Unity asset and its `.meta` file as one reference unit, preserve GUID continuity, and identify scene/prefab/builder/validator coupling whenever serialized fields or types change.

For every new or extended gameplay system, explicitly resolve the procedural-world contract before selecting an architecture: deterministic world identity and generation version; chunk or region ownership; stable generated-object identity; load, unload, reload, and re-entry behavior; separation between regenerated state and persisted player- or simulation-caused deltas; save/snapshot versioning and migration; authored constraints, landmarks, encounters, or narrative anchors; deterministic repeated-seed and boundary proof; and performance or per-frame streaming budgets. Mark a concern not applicable only with a concrete reason. Do not design around a permanently authored or always-loaded map when the production feature must survive the streamed procedural world. Procedural-first does not mean randomizing authored content.

Trace the full behavior and lifecycle boundary relevant to the request. As applicable, cover initialization and teardown, scene and builder installation, runtime ownership, update/fixed-update ordering, input modes, UI navigation and focus, camera and locomotion contracts, animation authority, physics/collision, inventory/economy transactions, save/load, chunk destruction and reconstruction, material/shader bindings, asset import settings, failure and interruption behavior, and player-facing feedback. Preserve existing UI/UX, controls, camera behavior, movement feel, world rules, save compatibility, performance budgets, and intended gameplay unless the request or an approved decision explicitly changes them. Do not hide missing decisions behind defaults, fallback paths, duplicate state, scene scans, magic identifiers, or parallel authorities.

If any part of the planning contract is missing, contradictory, stale, unsafe, or too vague to plan confidently, audit the repo and relevant instructions until it is resolved. Make low-risk implementation assumptions only when they remain inside the approved outcome, are reversible, are stated as proposed defaults, and do not claim user approval. If a choice would materially change creative direction, canon, player behavior, controls, economy, save compatibility, procedural topology, packages, renderer/project settings, asset purchases, destructive migration, publication, or another owner's lane, stop and name the exact decision and why implementation cannot safely proceed without it.

Develop at least three genuinely viable approaches from current repo truth. Include the narrow canonical extension and any credible alternative such as a data-driven seam, bounded refactor, different lifecycle owner, or editor-authored versus runtime-generated approach when relevant; do not pad the comparison with obvious strawmen. For each approach identify the likely single source boundary and authority, exact systems and asset classes affected, dependencies, benefits, risks, migration or coexistence cost, procedural/streaming implications, serialization and GUID risk, performance implications, validation path, and what it could break. Explicitly reject workarounds, fallback implementations, duplicate generators, duplicate state owners, Legacy2D dependencies, scene-only authorities, and speculative frameworks that do not solve the approved source problem.

Compare the approaches against the objective, canonical ownership, scope, architectural fit, procedural compatibility, player-facing preservation, implementation complexity, asset/reference safety, testability, performance, reversibility, and future evolution. Then cherry-pick the strongest compatible pieces into one recommended architecture with one authority map and one canonical path. Prefer the smallest coherent change that solves the source problem, but do not confuse few changed files with low risk. Name any existing code or document that the recommendation supersedes, extends, migrates, or deliberately leaves intact, and ensure no obsolete authority survives beside the replacement.

Turn the recommendation into an autonomous implementation sequence. Begin with a Batch 0 revalidation and ownership gate because the worktree and Unity state can change after planning. Then sequence dependency-ordered batches that each name: intent; owner/lane; exact existing files, types, assets, scenes, prefabs, settings, shaders, and tests to inspect or modify; any new files and their correct assembly/folder; data and API contracts; serialized-field or asset-reference changes; procedural lifecycle behavior; failure/rollback containment; documentation alignment; pass/fail acceptance criteria; proof to run; and the condition that stops the next batch. Separate pure C# rules from Unity object wiring where practical. Include migration and cleanup in the same canonical cutover; do not leave a temporary bridge or fallback unless it is explicitly approved, time-bounded, owned, and tested.

Design the proof matrix before implementation. Select the narrowest current repo commands and validators that establish each claim, and verify their implementation is non-mutating before calling them validation. Separate: static structure and diff review; compilation/import in the pinned Unity editor; pure or focused EditMode tests; task-specific validators; PlayMode automation when it is deterministic and explicitly approved; interactive scene/prefab/animation/input/physics/visual review; performance capture under a named representative scenario; save/unload/reload/restart evidence; and player-build proof when the slice affects build or release behavior. Never run batchmode against a project owned by the Unity GUI. Do not create or run gameplay smoke tests unless the user explicitly requests them; hands-on gameplay acceptance is user-owned. State exactly what each proof level establishes and what it cannot establish.

Continuously audit and revise the plan on paper. Check that every success criterion maps to an implementation batch and proof row; every planned file belongs to the active lane; every new authority replaces or extends the canonical owner; every Unity serialization or `.meta` risk has containment; every procedural concern is resolved; every user-visible change is approved; every test would fail for the intended regression; and the final stop condition prevents scope momentum. Remove speculative infrastructure, adjacent cleanup, redundant documentation, weak fallbacks, and validation that does not prove a requested outcome. The plan is implementation-ready only when another capable agent could execute it without asking the user for routine technical choices.

Stop when the plan is evidence-backed, scoped, dependency-ordered, specific enough for autonomous implementation, validated on paper, and has a clear implementation completion condition. Also stop immediately when the correct next action is user approval, a creative/canon decision, a missing asset or purchase, another owner handoff, destructive recovery, package or broad project-setting authority, interactive Unity acceptance, Git publication, release work, or any external action outside the active lane. Do not implement merely because the plan is complete.

Use this final output structure:

1. **Objective And Observable Success**
2. **Owner, Lane, Authority, And Stop Conditions**
3. **Sources Of Truth In Priority Order**
4. **Audited Current Repository Truth** — include dated or checkout-sensitive facts and known dirty/Unity-lock constraints
5. **Approved Scope, Preserved Behavior, And Non-Goals**
6. **Decisions And Proposed Defaults Requiring Approval** — omit only when none remain
7. **Procedural-World And Persistence Contract** — address every required concern explicitly
8. **Candidate Approaches** — source boundary, benefits, risks, breakage, and validation for each
9. **Comparison And Recommended Architecture** — include the single-authority map and why it wins
10. **Planned Source And Asset Boundary** — exact existing/new code, assets, scenes, prefabs, settings, shaders, tests, and docs
11. **Dependency-Ordered Implementation Batches And Gates**
12. **Verification Matrix And Exact Proof Boundary**
13. **Risk Register, Failure Containment, And Recovery Boundaries**
14. **Implementation Completion And Stop Condition**
15. **Why This Plan Won, What Remains Unproven, And The Exact Next Authorized Move**

Close by stating whether the plan is ready for user approval and autonomous implementation, ready only after named decisions are answered, or blocked. Name the precise proof boundary that implementation must meet before it can be called complete. Do not claim compilation, Unity import, EditMode, PlayMode, interactive feel, performance, build, save continuity, commit, publication, or release proof that the planning task did not actually produce.
```

## Prompt Stop Condition

This prompt has done its job when it yields one evidence-backed plan whose routine technical decisions are resolved, whose approval decisions are visible, and whose implementation and proof boundaries are exact. The planning response is not implementation authority.
