# Ironstone Formation Mineralization Plan

Status: implementation authorized (2026-09-23), Batch 1 visual feasibility paused at the production-mask gate. Visual acceptance and the old-save policy remain open; neither production topology nor a versioned save cutover is approved by this status.

Owner: Gottspan coordinates the Unity production change. The user owns the visual and economy decisions. Babineaux coordinates any approved Unity Editor bridge work; Gear Ball owns a later verified commit. The active implementation lane is the root TopDown3D Unity project.

## Objective and finish line

Ordinary generated physical rock formations can deterministically contain a finite Ironstone deposit. Mining a selected formation completes the existing gather action and adds Ironstone Ore directly to Booter's inventory. A mined-out formation keeps its mesh, collision, traversal role, and dust shelter. Its visual mineral signal and interaction availability reflect the saved remaining uses across chunk unload, reload, and game-state restore. No standalone Ironstone rock is generated in the new topology.

The visual target is iron-bearing material concentrated in true contacts and fractures, legible from the production elevated camera and grounded in the Broken World's restrained red/charcoal geology. Final color, coverage, and depletion look require user review of real Unity views.

## Current source of truth and constraints

- The user's direction and root `AGENTS.md` control scope. `WORLD_BASIS.md`, `WORLD_CREATOR_CHARTER.md`, `GROUND_CLUTTER_AND_NATURAL_OBJECT_SYSTEM.md`, and `IRONSTONE_MINING_AND_INVENTORY_SYSTEM.md` control setting and current contracts. The older Ironstone implementation plan rejected formation mining for its earlier objective; this new product direction supersedes that decision only after an explicit versioned cutover.
- `TopDown3DNaturalObjectPlanner.BuildChunkPlan` currently generates formations, then a separate `TopDown3DResourceNodePlanner` pass that excludes formation envelopes. `TopDown3DNaturalObjectDecorator` creates one formation root with member box colliders and three LOD renderers. `TopDown3DResourceNodeDecorator` creates standalone interactive rocks. `TopDown3DIronstoneNode` and `TopDown3DResourceWorldState` own interaction presentation and remaining-use deltas.
- The workbench mesher already writes a real contact-seam signal to vertex color R for fused geological shells. `BrokenWorldRockWorkbenchPBR.shader` reads that signal, while `BrokenWorldRockTriplanar.shader` serves production rocks. The production renderer currently combines baked members into three chunk-owned LOD meshes; authored mixed members can take a separate per-member material path. The workbench mask cannot be assumed to exist on those production meshes.
- `TopDown3DGameStateSaveService` now includes resource snapshots. Load first checks the full `WorldPersistenceManifest` against `ProductionWorldCreatorProfile.asset`, including its Decoration and Resource versions; it then checks the separate resource snapshot against `TopDown3DWorldSettings.asset`'s `resourceGenerationVersion`. The older Ironstone system document's statement that there is no whole-game save owner is stale. Save compatibility is therefore a release gate, not a theoretical future concern.
- Unity is 6000.4.0f1 with URP 17.4.0. `Temp/UnityLockfile` was present on 2026-09-23, so implementation must recheck Editor ownership before any CLI import or test. The worktree contains extensive user-owned rock, scene, settings, camera, and shader changes. Re-read live diffs and avoid editing overlapping files until ownership is clear.

## Procedural and persistence contract

1. **World identity:** select mineralization from stable formation identity plus a dedicated resource/mineralization version and fixed hash salt. Do not use chunk load order, runtime generation tokens, `string.GetHashCode`, or mutable GameObject names. `WorldRockFormationPlanner` creates its `WorldFeatureId` in the Decoration namespace, which includes topology, coordinate, and Decoration versions. Mineralization can be independently retuned through its resource version only while the underlying formation ID and eligibility remain stable; changes to formation identity or realized membership can orphan its delta. Test that boundary explicitly.
2. **Ownership:** the same owner chunk that realizes a complete formation owns its mineralization record and streamed component, even when members cross a border. Eligibility must produce the same result after a local-origin rebase. Neighbor checks, if used for Ironstone spacing, must be symmetric and independent of load order. Do not add a second geographic formation generator.
3. **Authored constraints:** evaluate the formation's actual realized size, accessible faces, terrain geology, reserved routes, spawn clearance, and authored template eligibility. Preserve the formation plan and existing location when resource tuning changes. Include the active authored mixed template in the eligibility and visual proof; it is already assigned in production settings. Calibrate ore per world area and median travel distance from a fixed-seed sample of the current standalone system, then compare the new eligible-formation distribution. A flat probability alone is only an experimental control; do not add rocks solely to hit a resource quota.
4. **Stable deposit and delta:** use one resource ID derived from the canonical formation ID and resource generation version. Store only remaining uses in the world-root resource state; never serialize a mesh, material, or chunk component as depletion truth. Keep `MaximumUses` and `YieldQuantity` authored. The initial economy is the current one-use, one-ore behavior unless the user changes it.
5. **Unload, reload, restore:** reconstruct the same selected formation, attach the resource view, and read its saved delta. Depletion must not disable a formation's physical colliders. Save capture, validation, application, rollback, and restart must treat the new topology consistently.
6. **Versioning:** changing resource topology requires a deliberate cutover across two distinct version authorities: World Creator's Resource version in `ProductionWorldCreatorProfile.asset` and the resource snapshot version in `TopDown3DWorldSettings.asset`. Any required Decoration-version change is a separate, wider world-identity change. Current full-manifest and resource-snapshot checks reject mismatches before applying inventory or position, so simply incrementing a version would reject the whole save. Old standalone-node deltas contain only an ID and remaining uses, with no formation mapping; do not promise an exact conversion. Choose and prove a policy for the complete older save before switching defaults.

## Candidate visual approaches

| Approach | Boundary and benefit | Cost or failure mode | Experiment verdict |
| --- | --- | --- | --- |
| Fused-shell seam mask | Reuse workbench vertex-color R on an editor-baked production shell; precise visible contacts and one renderer per LOD | Requires a changed production bake for all eligible families and authored templates; LOD mask preservation and GUID/reference safety are substantial | Test on one disposable workbench formation first; do not make runtime Boolean fusion a dependency |
| Combined-member contact mask | Compute contact proximity on each chunk-owned combined LOD mesh from the formation's member transforms; preserve existing baked source meshes | Bounds painted hidden or misplaced overlap; actual mesh-surface distance was slow and still produced spots rather than visible veins | Rejected for runtime after fixed-camera renders and 4.2-8.8-second LOD0 mask timings in the isolated Editor |
| Small seam geometry/decal accents | Emit a few seed-stable seam strips or URP decals on selected contacts; strongest close-up depth | More draw calls/objects, projection spill, LOD and unload bookkeeping | Reserve for a bounded mined-fracture feedback experiment if masked shading lacks depth |

The existing world-space crack and luster textures can break up a true contact mask. They cannot locate contacts by themselves. Test the mask in a debug view before evaluating color or metallic response.

Research basis: [Unity Mesh.SetColors](https://docs.unity3d.com/6000.0/ScriptReference/Mesh.SetColors.html) documents compact `Color32` storage; [Mesh.CombineMeshes](https://docs.unity3d.com/6000.0/ScriptReference/Mesh.CombineMeshes.html) supports the current single-material combined LOD path; [SRP batching guidance](https://docs.unity3d.com/6000.0/Manual/DrawCallBatching-Properties.html) warns about property blocks; and [URP decals](https://docs.unity3d.com/6000.0/Manual/urp/renderer-feature-decal.html) provide a possible local accent. Match these choices to the pinned URP package during implementation. The existing hand-written URP rock shader is the first shader extension point; adding Shader Graph solely for this effect would create a second material authority.

## Proposed visual experiments

Use a disposable workbench preview and a fixed elevated camera, with the same neutral formation, lighting, and screenshot framing for each variant. Do not edit the approved source formation or production scene for an unaccepted look.

1. **Contact-only:** oxidized red-brown mineral confined to seam-mask R. Record near and gameplay-distance screenshots plus a mask-only view.
2. **Branching veins:** permit thin seeded branches from high-confidence contacts along the workbench's existing formation-scale fracture field. Limit branch length and coverage so broad exposed faces remain ordinary rock.
3. **Richness ladder:** compare sparse, medium, and dense mineral coverage with fixed geometry. Measure whether each remains readable at the gameplay camera without looking like a uniform resource tint.
4. **Depletion scar:** compare nearly clean stone, dark empty seams, and a subdued residual rust stain. The resource is unavailable in every depleted variant; choose the legible state after user review.
5. **Optional strike feedback:** a short-lived dust/chip or local fracture accent at the mining contact. Keep this separate from persistent mineral appearance and defer if it requires new renderer features.

Experiment outputs should include screenshots at fixed views, shader variant/mesh notes, and a short selection record. They are visual proposals, not canon or production acceptance.

## Recommended single-authority architecture

- `WorldRockFormationPlanner` and `TopDown3DGeologicalRockAdapter` continue to own where and how formations exist. A revised resource planner receives their realized formation plans and returns an immutable mineralization assignment keyed by formation ID. It neither adds nor removes formations.
- The canonical chunk plan carries those assignments alongside physical formations. Decoration creates the formation once, then attaches an Ironstone interactable to the same root. Existing inventory and world-root resource state remain the only mutable economy authorities.
- Give the interactable an explicit set of eligible physical member colliders and a reachable interaction point near the selected face. `TopDown3DGatherActionState` currently rechecks availability and distance during the action, but not line of sight; decide and test whether changing cover must cancel mining. Update `TopDown3DInteractionController` line-of-sight validation for a target with multiple colliders, including rays that strike another member of the same formation. A distant formation center must not make the whole structure mineable through itself. Keep all physical colliders enabled after depletion.
- Use a bounded shared material palette for ordinary, active, and depleted appearance across the existing regular/dark/teal rock surface families and the authored mixed material. Preserve each family's base look; mineralization changes the veins, not the entire rock color. Unity warns that per-renderer `MaterialPropertyBlock` disables SRP Batcher compatibility, so benchmark before introducing it in the production stream. The editor workbench may retain its current property-block controls.
- Encode seam and mineral richness in available mesh channels only after checking the current baked families and authored template channels. Keep the mask available across LODs. The ordinary formation path calls `UploadMeshData(true)` after making its combined LOD meshes, so any runtime mask must be written before that upload; depletion must switch appearance without editing a discarded CPU mesh. If the combined-member method cannot accurately represent seams, promote an editor bake for eligible formation families; do not create a parallel runtime fusion system.

## Proof boundaries and stop conditions

- Static review and `git diff --check` prove scope/format only. Focused EditMode tests prove deterministic planning, transactions, and reconstruction, not shader appearance.
- Unity 6000.4.0f1 import and Metal shader compilation prove the assets compile, not that the veins read well. Use the user's active Editor through the approved bridge or an isolated project mirror; never launch batchmode against the locked project.
- Fixed-camera comparison proves local visual readability. Production scene inspection and profiler/Frame Debugger evidence must check all three LODs, ordinary versus active versus depleted formations, draw calls, material batches, and decoration time. A target Windows Player claim needs its own build/performance proof.
- Save proof must cover pristine, partly used if `MaximumUses > 1`, depleted, chunk unload/reload, successful restart restore, and old-snapshot policy. A snapshot round trip alone does not prove disk restore.
- Stop implementation if the only viable mask requires replacing accepted formation geometry, if performance exceeds the representative baseline, if a save migration would discard existing progress without an explicit user decision, or if required visual acceptance has not been given.

## Open product decisions before production cutover

1. Old saves: preserve an older world version, implement an explicit whole-save transition that retains player/inventory state but resets old node depletion, or declare the older save incompatible. Exact depleted-node-to-formation mapping is unsupported by the current snapshot data. This choice affects whether older full game-state saves can load.
2. Visual: choose the experiment's vein density and depleted scar. The plan proposes dark oxidized contacts with limited branching as the first review candidate.
3. Eligibility: should singular boulders ever contain Ironstone, or only formations with visible multi-rock seams? Proposed first pass: all ordinary and authored multi-member formations with a reachable contact; inspect measured distribution before locking it. Single boulders would need a fracture-only visual rule.

Planning is complete. Production is complete only after the chosen visual, deterministic topology, interaction, save compatibility, Unity import, focused tests, streamed presentation, and representative performance gates pass. The current workbench experiment exposes contact-only veins, restrained fracture branching, depletion stain, and a mask-debug view without changing production material defaults. It uses a separate lightweight URP preview shader because the existing workbench PBR shader exceeded Metal's sampler limit in the live Editor log before this experiment. The experimental shader is intentionally neutral stone, not the production material palette.

Batch 1 evidence (2026-09-23): isolated Unity 6000.4.0f1 import and two focused EditMode tests passed, confirming fused workbench seam colors and a nonuniform collider-box contact signal on one fixed-seed regular formation at all three production LODs. A temporary fixed-camera Metal render of a five-member production formation showed that the box-proximity mask is largely hidden or misplaced on visible surfaces; branching did not improve it. Thus a numeric nonzero-mask test is not visual feasibility proof. Do not wire this mask into runtime or claim the production visual gate passed. The next visual decision is whether to pursue a bounded seam-geometry/decal accent, a reference-safe editor-baked fused shell for eligible formations, or a different surface-contact method.

Follow-up surface-distance experiment (same date, isolated mirror only): hashing actual member triangles yielded no LOD2 mask at all for two of eleven regular formations in the fixed 121-chunk sample. A high-contact eight-member example produced isolated bright spots rather than a coherent seam at the elevated camera. Its LOD0 mask had 2,448 nonzero vertices out of 41,340 and took 8,771 ms to compute in the Editor. The earlier five-member example took 4,217 ms for LOD0 and remained nearly invisible. This is not a runtime decoration candidate. The source-triangle experiment exists only in the temporary mirror, not in production assets. The failed box-contact helper and its narrow test were also removed from the repository after recording their evidence; neither method should be wired into streaming.

Batch 0 economy measurement (same date): with production settings seed `24681357`, distant spawn exclusion, and chunks `(-5,-5)` through `(5,5)`, the old planner generated 40 standalone nodes in 121 chunks (0.331 per chunk), while the same plans contained 12 physical formations (0.099 per chunk), all with multiple members. Consequently the proposed one-use, one-ore formation cap cannot preserve the old site density even at 100% mineralization. Resolve whether Ironstone should become much rarer, each site should yield more, or formation supply itself should change. This is a product/economy decision, not a planner tuning detail. The old-save policy also remains to be chosen before Batch 5.
