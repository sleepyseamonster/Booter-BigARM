# R2 — bounded live authoring

Implemented 2026-09-15 under the [correction plan](./ENGINE_CORRECTION_PLAN.md). Closes A05 for the supported local Mac host. [Evidence](../Evidence/R2-live-authoring/result.json) includes CPU/domain checks and a real CLI-to-Workbench exchange. **R3 snapshot rendering and the Scene View manipulation contract are next.** Authored entities are not yet displayed by the fixture renderer; visual gizmos, shared play sessions, live save/load and native Windows transport remain separate work.

## Delivered architecture

`engine_authoring` now contains the scene domain, shared command adapter, host and local transport. Runtime-only targets retain `engine_core` without authoring/thread/transport dependencies. The Workbench instantiates the host when an explicit `--authoring-socket` is supplied. The optional startup scene loads before the frame loop; no scene is permanently cooked or written by these commands.

One dedicated authoring thread owns publication. It copies the immutable base state/history into an independent candidate, invokes the shared domain handler, prepares a history-free read snapshot and serializes the terminal receipt. Only then does it recheck the base revision and cancellation, swap the authoritative candidate/read snapshot, and retain the applied receipt in one short critical section. Retired documents release outside that section. No model call, socket read, JSON preparation, physics or GPU access occurs in the render loop. R3 will consume the published read snapshots. Acquiring a frame snapshot uses an atomic shared-pointer load, so queue admission, receipt copying and inspection do not hold the frame reader behind the command mutex. This does not assert that the standard library implements shared pointers lock-free.

Both the older in-process adapter and live host call `SceneAuthoringAdapter::execute`; there is one structural-edit implementation. It supports create, duplicate, subtree delete, transform, preserve-world reparent and metadata inside atomic transactions, plus preview validation and undo/redo. Preview reports the proposed revision and changed/created IDs without publication or history changes. Ephemeral rendered drag preview belongs to R3. The legacy in-process queue is a compatibility/test surface, not the endpoint transport or a second scene authority.

Read snapshots share validated entity/index/affine state without retaining undo/redo history. Four revisions are pinned by the host. Pages are built from indexed entities and cached world matrices, without repeatedly serializing the entire document or recursively walking parents. Readers request an exact revision; an expired revision rejects explicitly rather than mixing pages from different scenes. External C++ snapshot consumers own their leases and must release them; the four-slot host bound does not limit an external consumer that retains snapshots indefinitely.

## Admission, receipts and shutdown

- Requests: at most 256 KiB and 32 levels; duplicate/unknown keys, unsupported operations and malformed types reject. Pending work, including the preparation in progress, is bounded by 128 requests and 8 MiB of serialized request bytes.
- Results: at most 64 KiB per wire response and 64 entities per inspection page. Large entities can reduce page length. The scene domain remains 1,024 entities/64 parent links/1 MiB durable envelope.
- Retention: at most 512 records and 8 MiB combined serialized original-request/receipt bytes. Admission reserves a maximum-size terminal receipt plus the exact canonical request. Pending receipts cannot be evicted. Completed receipts use their actual encoded size; exact original requests are retained to detect ID collisions. These are encoded-payload budgets, not total process/allocator memory measurements.
- Identity: every scene read, mutation and receipt action names document ID and the advertised random live epoch. Mutations require a nonzero expected revision. Every accepted request ID advances a per-epoch unsigned high-water mark. A retained retry returns its existing receipt; a different payload under the same ID returns `request_id_conflict`. A missing ID at/below the high-water mark returns `expired_or_unknown` and is never replayed. Multiple clients must reconcile ID conflicts before issuing a fresh request.
- Results distinguish `queued`, `preparing`, `previewed`, `applied`, `rejected` and `cancelled_before_apply`. Cancel returns `cancellation_requested` until the owner resolves it. Cancellation after application returns the applied receipt. A transport disconnect cannot turn an applied command into a rejected command. Nothing here claims durable/crash-persistent exactly-once edits.
- Stop rejects new requests, cancels pending/preparing work and joins the owner. Publication already completed remains applied. Endpoint destruction stops ingress before host teardown, waits for its transport thread and removes only the socket inode it created. No background host is left running by the technical check.

The Mac transport accepts one newline-terminated JSON request per connection through a private Unix-domain socket. It requires an existing user-owned directory with no group/other permissions, sets the socket to 0600, refuses to replace existing endpoints, bounds client I/O to two seconds and services stop in short polling intervals. Transport requests are serialized; a stalled local client can delay other command clients up to that bound, while frame work remains independent. The platform adapter explicitly reports unsupported on Windows; the named-pipe implementation and native evidence remain in the Windows gate, not a claimed Mac-to-Windows success.

## Verification and practical limits

Four focused native cases pass: core operations/documents, existing scene contracts, R1 corrections and the new bounded-host suite. They cover direct/live result equivalence, structural command parsing, immutable snapshots, exact-identity retries, stale revision/epoch rejection, undo/redo, nonmutating preview, receipt expiry without replay, queue/byte/receipt bounds, oversized terminal-result rejection before live publication, flat/deep 1,024-entity page extraction and terminal shutdown receipts. R1's allocation-injection suite passes against the expanded adapter; the new host is not claimed to have exhaustive allocation-fault or scheduler-interleaving coverage.

The real Workbench binary runs in its bounded **headless authoring mode**, using the same host construction as normal viewer startup. The Python CLI creates and transforms a neutral entity and reads the independent expected translation from its world matrix. The technical check also verifies retry after interrupted delivery, duplicate JSON rejection, refusal to steal an endpoint, incomplete-client shutdown, cleanup and fresh restart epoch. This proves application wiring and transport behavior; SDL/gameplay were not initialized and no new pixels or GUI acceptance are claimed.

The evidence separates candidate preparation from the no-allocation owner adoption section and records one 1,024-entity page traversal. These are observational CPU timings for this Mac/build, not statistical frame percentiles, input-to-photon latency, a total-memory high-water mark or a Windows FPS claim. R5 owns the representative graphics/resource measurement.

No world generator, seed, generated-object identity, authored constraint, chunk residency or persisted runtime delta changes. The host edits authored source documents only; unloading generated runtime content cannot mutate these snapshots. Live save/load waits for R4's asynchronous conflict/recovery/durable-acknowledgment boundary. No UI widgets or preserved Unity content were edited.
